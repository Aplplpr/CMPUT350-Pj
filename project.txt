Liam:
I mainly worked on the gameplay systems and several engine interfaces. I implemented line and circle geometry functions, cubic Bezier curves, and the NotificationManager, and updated the GameObject, GraphicsObject, and CollisionObject interfaces to support new rendering, collision, and notification systems. 
I created three distinct enemy types with unique health values, attack trajectories, shooting patterns, and point rewards. Enemies travel along Bezier‑curve paths, and curve slope values determine their in‑motion rotation. I also built the core Galaga class to govern overall game flow, managing enemy waves, player lives, scoring, level progression, and game resets.

For key design choices, I used state machines to manage both high‑level game flow and individual enemy behaviours, enabling clean transitions between enemy entry, formation, attack and return phases.
To keep enemy movement speed consistent, I sampled Bezier curves to calculate path distances instead of directly modifying curve parameters. I applied weak_ptr within NotificationManager and bullet parent references to avoid unintended extension of game‑object lifespans.
I also separated core game logic from visual rendering: the Galaga class handles game‑rule logic while GUIContext takes charge of on‑screen information display.

The Galaga class uses five main states:
1. Waiting: The game waits for the player to press 5 to insert a coin and 1 to start.2. Startup: The game resets the score, lives, and level, then creates the player. After 60frames, it enters the Waves state.
3. Waves: The game spawns five waves of eight enemies, for a total of 40 enemies. Each
enemy follows a Bezier path to its formation position.
4. Gameplay: After the enemies reach their formation, the game starts selecting enemies to
attack. The player can move and shoot enemies to earn points. When all enemies are
destroyed, the game advances to the next level. If the player dies but still has lives, the
game waits before respawning the player.
5. GameOver: When the player runs out of lives, the game displays the Game Over message.
After 150 frames, the game resets to Waiting.


Siqi:
I mainly worked on the engine-side systems, including GameContext and EngineView integration, DrawContext transformations, keyboard notification mapping, object iteration, and the advanced collision system. I also connected these systems together in the main GameEngine loop.

For some of the implementation choices, I kept collision points in world space while doing collision checks, and only converted them back into each object's local coordinates when calling CollisionEnter. I first use the transformed bounding boxes to quickly rule out objects that are clearly not colliding. If the bounding boxes overlap, the engine then checks the actual Line, Circle, or Rect collision shapes to determine whether a real collision occurred. For object cleanup, I kept the same approach we used in the earlier version of the engine, where living objects are moved to the front of the vector and the vector is resized once instead of erasing dead objects one by one.
